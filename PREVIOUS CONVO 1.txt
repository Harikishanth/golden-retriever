Here's the reality check on the 0.97+ target:

**Current approach (BM25 + LightGBM):**
- Expected score: 0.78–0.84
- Recall ceiling: ~0.93 (blocking limitation)
- **Cannot reach 0.96+** no matter how good the classifier is

**To reach 0.97+, you need:**

1. **Dense retrieval** (sentence-transformers bi-encoder)
   - Raises recall ceiling to 0.97–0.99
   - Requires: GPU (T4/A10), ~2–3 hours to encode 11M entities
   - Expected gain: +0.05–0.10 → puts you at 0.83–0.94

2. **Cross-encoder** (DistilBERT/mDeBERTa fine-tuned on entity pairs)
   - Much better matching than LightGBM
   - Requires: GPU, ~1–2 hours to fine-tune, ~8–20 hours for test inference (86M pairs)
   - Expected gain: +0.03–0.07 → combined 0.87–0.96

3. **Ensemble** (LightGBM + cross-encoder fusion)
   - Stacking the two scores
   - Expected: 0.90–0.97+

**The compute bottleneck:**
- Current EC2 (r5.2xlarge) is **CPU-only** — cannot run transformers at competitive speed
- You'd need a **GPU instance** like g4dn.xlarge (T4 GPU, $0.526/hr) or g5.xlarge (A10G, $1.006/hr)
- Total time with GPU: ~12–25 hours for dense + cross-encoder pipeline

**The honest answer:** 0.97+ is achievable but requires GPU compute and ~12+ hours of pipeline time. If you're willing to spin up a GPU instance, it's doable before the Sunday deadline. Without transformers, the ceiling is ~0.93.

Pipeline architecture (6 modules)

1. io_utils.py — streaming TSV reader with auto-detection of EC2 vs local
   data paths. Handles tab-separated format correctly (addresses contain
   commas). Also writes submission files with deduplication.
2. normalize.py — text normalization: accent folding, legal suffix removal
   (Inc/Ltd/SARL/etc.), noise cleaning (emails, hashtags, URLs), house number
   extraction, address token filtering with region abbreviation mapping (US
   states + Indian states), city/street extraction. French legal suffixes are
   included for the test-only France entities.
3. blocking.py — BM25-style token retrieval. Builds a country-scoped inverted
   index keyed by (country, type, token) where type is N (name), A
   (address), or H (house number). Candidates are scored by IDF-weighted
   token overlap with separate weights: name tokens ×2.0, address tokens
   ×1.2, house numbers +8.0 flat. A MAX_POSTING=2000 guard skips overly
   common tokens. Returns the top 150 candidates per S1 entity, ranked by
   score.
4. match.py — 17 features per candidate pair: IDF-weighted name Jaccard, name
   containment, character trigram similarity, house number agreement,
   address token Jaccard, exact address match, city agreement, name rarity
   (binary + continuous log version), name length ratio, Jaro-Winkler, TF-IDF
   cosine, four rapidfuzz scores (token sort/set/partial on name, token sort
   on address), and phonetic match via jellyfish Soundex. Includes a
   hand-rolled Jaro-Winkler implementation as fallback. Loads model weights
   from model.json for inference.
5. fast_features.py — vectorized batch feature computation using
   rapidfuzz.process.cdist for the test run. Computes 15 features (the
   original set without phonetic/rarity-log) in a batched manner, roughly 10×
   faster than the per-pair loop.
6. evaluate.py — macro F0.5 scorer matching the contest's definition: empty
   prediction on a true singleton scores 1.0, any wrong prediction on a
   singleton scores 0.0.
7. run.py — the main entry point with two modes:
   - holdout: loads train data, samples 100k S1 entities, builds the BM25 index, featurizes all pairs, trains LightGBM (500 trees, 63 leaves, auto
